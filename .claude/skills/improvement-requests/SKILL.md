# WACA Loop 改善要望 — 受けて、直しきって、返す

正典: `docs/SPEC_improvement_requests.md`。その方針に反する実装をしないこと。

## 1. セッションの入口で（§4）

waca-loop リポジトリで作業を始めたら、**最初に一度だけ** `list_improvement_requests` を呼ぶ。
未対応（`open`）があれば、**その回の最初の応答の冒頭に出す**。

出すのは **件名・起案者ラベル・上がった日だけ**。本文は、管理者が1件選んだときに展開する。
一覧を全部展開すると、本来の用件が要望の山に埋もれる。

「最優先」は AI が計算した優先度ではない。**未対応の要望を他の話題より先に出す**という
提示順のことである。`priority` 列は無い（§2）。序列を作らないこと。

要望が無ければ**何も言わない**。「要望はありません」と毎回書くのは提示ではなく雑音。

## 2. 1件を選んだら（§4）

そのセッションで **設計 → 実装 → テスト**まで通す。

1. 着手時に `set_request_status(request_id, "designing")`
2. 実装。`src/` か `sql/` を触ったなら、コミット前に **`spec-guardian` と
   `acl-privacy-auditor` を必ず通す**（ブロック権あり）
3. `pytest` 全緑・`ruff check .` クリーン
4. 完了時に `set_request_status(request_id, "implemented", resolution="<実装内容の要約>")`。
   デプロイまで行ったら `"released"`

`resolution` はそのままシートに出て**起案者が読む**。「fix」ではなく、
何がどう変わったかを一文で書く。

## 3. Issue は下書きまで（§1-2）

GitHub Issue の作成は管理者の承認が要る（CLAUDE.md）。**スキルが押さない。**
タイトル・再現手順・影響範囲を生成して `gh issue create` のコマンドを提示し、
押されたあとに `issue_url` を埋める。

## 4. 記録するとき（§3.1・§9.2）

利用者が **明示的に**「WACA Loopのここを直してほしい」と述べたときだけ
`report_improvement_request` を呼ぶ。

**会話から自動で拾わない。** 拾うと SFAQ の判断ナレッジと混ざる。SFAQ は「組織の仕事の判断」で
資産として残り、改善要望は「道具への注文」で直れば役目が終わる。**寿命が違うものを
同じ層に置かない**（§9）。同じ理由で、`propose_candidates` の原料に WACA Loop 自身への言及を
入れないこと。

- `kind` は `bug` / `improvement` / `other`。**迷ったら `other`**。
  無理に寄せると「不具合の件数」を数えたときに混ざっているのに気づけない（§1-9）
- 複数部門に所属する人の要望は `owner_unit` を**尋ねる**。推測しない（§3.1）
- 匿名を希望されたら `anonymous=True`。**事後に取り消せない**ので一度だけ確認する

## 5. 見送り（§8）

`wontfix` を付けられるのは **owner ユニット（org.toml の [units] owner。WACA Loop の管理者）を持つ人だけ**。スチュワードでも通らない。
ほかの状態は途中経過の記録で次の更新で直るが、見送りは「直さないと決めた」結論で、
起案者への説明責任が伴い、放っておくとその要望は二度と §1 の提示に出てこない。

**AI が見送りを提案するのは構わないが、決めるのは人**である。

## 6. 直したあとに学びが残ったら（§9.3）

要望そのものは SFAQ に入れない。ただし実装後、**「なぜそう直したか／なぜ見送ったか」が
判断として価値を持つ**ことがある。そのときだけ、人が SFAQ に起こす。
`raise_lesson_from_task` と同じで、**写しではなく人が書く**。
