# テスト戦略

## 0. 方針

レビューには終了条件が無い。角度を変えれば何かは出るので、いくらでも続けられる。また、欠陥は**同じ型で
繰り返し現れやすい**。WACA Loop は、レビューの回数ではなく、**欠陥の型を機械で落とす**テストで品質を
保つ。

---

## 1. 前提 — テストが実行しないコードはどこにあるか

スイートはクラウドの資格情報なしで動く(CLAUDE.md の約束)。そのため、**BigQuery 双子クラスの中の
コードはオフラインでは実行されない**。ストア系の未実行行は、ほぼ全部がそこに集中する。
**「動かない」と「見ていない」は違う。** 欠陥が見つかりやすいのも、テストが1行も実行しないこの場所である。

再発しやすい型は2つある。

- **双子の乖離** — BigQuery 側にだけメソッドが無い/条件が違う
- **ゲートの無い第二の読み口** — 同じテーブルを ACL を通らずに読む経路

---

## 2. 設計

### 2.1 4種類のテストに分ける

| # | 種別 | 何を保証するか | 実行環境 |
|---|---|---|---|
| **W1** | **白箱・純ロジック** | 判定式・正規化・ACL の述語 | オフライン |
| **W2** | **白箱・双子適合** | **InMemory と BigQuery が同じ振る舞いをする** | オフライン(偽クライアント) |
| **W3** | **白箱・SQL 契約** | 生成される SQL の形(ゲート句・パラメータ・列) | オフライン |
| **B1** | **黒箱・MCP 契約** | 実際のサーバーに MCP で話しかけ、複数ペルソナで観察 | ローカル起動 or 本番 |

### 2.2 W2(双子適合)

**同じ振る舞い仕様を、両方の双子に対して流す。** ストアごとに「この操作をしたらこう返る」を一組書き、
InMemory と BigQuery の両方で実行する。BigQuery 側は**偽クライアント**を挿し、実際に組み立てられた SQL を
インメモリの表に対して評価する(クラウド資格情報は要らない)。

満たすべき性質:

| ID | 性質 | 防ぐ欠陥の例 |
|---|---|---|
| W2-1 | 公開メソッドの集合が一致する | 片方にだけメソッドが無い |
| W2-2 | 同じ引数で同じ行が返る(可視・不可視・存在しない) | 片方だけゲートが抜ける |
| W2-3 | ACL 引数に既定値を持たない | `viewer=None` の素通り |
| W2-4 | 書き込みの条件が守りの条件と一致する | 引き当てのパラメータ未使用 |
| W2-5 | 守りの評価順序が一致する | 数える前に落とす順序の違い |
| W2-6 | 同じ文字列を埋め込む/同じ本文を選ぶ | 前処理(TRIM など)の差 |
| W2-7 | 壊れた入力で同じように失敗する | payload の二重エンコード |

### 2.3 B1(黒箱)

内部を知らない立場で、**MCP プロトコル越しに**確かめる。

- 全ツールの名前・必須引数・戻り値のキーが宣言どおりか
- 認証なしは通らないか(fail closed)
- ペルソナ別に、見えてはいけない行が返らないか
- 例外メッセージに値・氏名・逐語が混じらないか

### 2.4 終了条件

**「もう一周」ではなく、次を全部満たしたら出す。**

1. W2 の性質 W2-1〜7 が全ストア対で緑
2. 修正した欠陥が、**それぞれ1本以上のテストに紐づいている**。紐づけは**変異テストで確認する** —
   修正を戻してそのテストが赤くなること。塞いでいない指摘にはテストを書かない(穴を緑にしない)
3. B1(黒箱・MCP 契約)が全ツールで緑。**検査できなかったツールは「問題なし」に数えない**
4. **BigQuery 双子の振る舞いが表明で覆われている。** 未実行行数は条件にしない — 偽クライアントで
   空打ちすれば行は実行され、安全性を上げずに数字だけ達成できるためである。条件は次の3つ:
   - a. 閲覧者ゲートの要る読み取りは、**句の全文**が SQL に入り、副問い合わせなら**行の対応の等式**が
     あること(「ACL らしい語がある」では不可)
   - b. 見える行・見えない行・存在しない行で、**双子が同じものを返す**ことの表明があること
   - c. BigQuery 側の修正を戻す変異で、対応するテストが**赤になる**こと

   未実行行数は**進捗の目安**として見るが、達成条件にはしない。
5. 1〜4 を満たしたうえで、レビューで重大な問題が出ないこと。

## 3. 実装されているスイート

### 3.1 B1 黒箱契約スイート(`tests/test_b1_black_box_contract.py`)

終了条件3の「検査できなかったツールは『問題なし』に数えない」を機械に持たせる。

やり方は名簿である。`PROBES`(叩き方)と `REQUIRED`(必須引数の集合)を持ち、**生きたツール表と集合一致する
ことを表明する**。ツールを足した人は、両方に1件書くまで赤いままになる。オフラインで走る(FastMCP に
InMemory ストアを載せ、`call_tool` で外から叩く)。

| 検査 | 内容 |
|---|---|
| 名簿一致 | 全ツールが漏れなく検査対象に入っている |
| 必須引数 | 宣言された必須の集合が固定値と一致し、省くと断られる |
| 未配線を緑にしない | `not configured` で落ちたら失格(＝検査できていない) |
| 漏れ | 応答・例外の文面に氏名・連絡先・逐語が出ない |
| ペルソナ | 部外者の件数がメンバーを超えない |
| 逐語の入れ物 | どのツールの**宣言**にも `prompt`/`transcript` 等が無い(T6 を外から) |

必須引数の期待値は `REQUIRED` として外に固定してある。宣言から導くと、必須を外す変異で `required` が空になり、
テストが自分を skip して緑になるためである。*変異チェックでは「テストが効くか」だけでなく「テストが自分を
無効化しないか」も見ること。*

限界: ペルソナ比較が実際に件数比較まで届くのは一部のツールだけである(残りはゲートや例外で返る経路)。
届いていること自体は `test_the_persona_comparison_actually_reaches_these_tools` で別に表明している。

### 3.2 W2 双子適合スイート(`tests/test_twin_conformance.py`)

**メソッドを名指しせず、性質として検査する**。新しいメソッドが増えても自動的に対象になる。

| 性質 | 内容 |
|---|---|
| W2-1 | 公開メソッドの集合が一致(意図的な非対称は理由つきで列挙) |
| W2-1b | 共有メソッドの**引数名まで**一致 |
| W2-3 | `viewer` に既定値を持たせない(省略できる ACL ゲートは、いつか省略される) |
| W2-2 | **viewer を取る BigQuery の読み取りは、生成 SQL に ACL ゲートを含む** |

W2-2 は、閲覧者をコンストラクタで束ねる型(terms/questions)と引数で受ける型(persons)の両方に対応する。
呼べなかったメソッドは **skip にせず失敗**させる — 未検査を「問題なし」として緑にするのが、この手の
仕掛けの典型的な壊れ方だからである。ゲート句は別名(`p.` `q.` `f.`)付きで埋め込まれるため、
**パラメータ名で照合**する。

対(`InMemoryX` / `BigQueryX`)は**パッケージ全体から自動で見つける**。新しいストアを足した人がこの
ファイルを知らなくても検査対象になる。閲覧者ゲートを持たないストア(証跡・候補・アンケート・OAuth
クライアント・台帳)や、意図的な非対称(`InMemoryPolicyStore.add` など)は理由つきで列挙してある。

### 3.3 行を返す偽 BigQuery クライアント(`tests/fake_bq.py`)

組み立てた SQL を **SQLite へ翻訳して実際に評価する**偽クライアントである。
`tests/test_w2_row_parity.py` で、双子が**同じ行を返す**ことを表明する(条件4b)。

**未対応の構文は黙って通さず落とす**(`UnsupportedSql`)。未検査を「問題なし」として緑にするのが、
この手の道具の壊れ方だからである。

**2つの検査は互いを覆わない**。SPEC_phase1 §3.3 の二重ゲートの片方(SQL 側)を外しても行は変わらない(in-process 側が
拾う)ため、行の一致だけでは検出できない。それは W2-2(句の全文＋行対応)が捕まえる。
**両方あって初めて「二重ゲートが二重のまま」と言える。**

### 3.4 テストを書かないもの

塞いでいない指摘にはテストを書かない(終了条件2)。既知の限界は各仕様書の未決事項に記載する。
