# SPEC: 台帳カバレッジ(記録率)の改善

SPEC_ops の **R3b / R3c / R7** および P1 を具体化する。

関連: `docs/SPEC_ops.md` §5(R1/R1b/R2/R3a/R3b/R4/R8/R9)、`docs/HOOKS_SPEC.md`(クライアント側フック)、
`scripts/coverage_report.py`。

---

## 1. 起きうること

- **登録者と実利用の乖離**: `oauth_identity_map` に一括登録しても、登録後に一度も接続しない人が
  出うる。その場合、台帳の行は一部の人に偏る。
- **接続を試みて弾かれている人に気づかない**: Cloud Run のログに `not in oauth_identity_map` による
  拒否が残っていても、見る仕組みが無ければ気づけない(登録が接続試行の**後追い**になる)。
- **記録漏れ**: (a) サーバーが観測できる範囲(R3a: policy_check したのに usage_recorded が無い)は、
  「ポリシー確認はした」人しか捕まえられないので実態を過小評価しうる。(b) 長い会話ではルールが薄れ、
  記録が落ちうる。**正確な記録率を出すには計測基盤が要る。**

## 2. 原因の分類

| # | 原因 | 種別 |
|---|---|---|
| **A** | 登録済みの人が**一度も接続していない** | オンボーディング |
| **B** | 接続を試みた人が identity_map 未登録で**弾かれ、気づかれない** | 運用(検知なし) |
| **C** | 接続済みでも**長い会話でモデルが log_usage を呼ばなくなる** | クライアント側 |
| **D** | **真の記録率を計測できない**(分母がサーバーから見えない) | 計測基盤 |

A と B は利用の母数に、C は記録の質に効く。母数が少ないままでは記録率を上げても全体は動かないため、
A/B の検知(C1)を先に置く。

## 3. 対策

### C1(A/B 対応)— 接続状況の可視化と未接続者の検知

`scripts/coverage_report.py` に **登録者 × 接続実績** のビューを持たせる。R3a の集計は「接続した人」しか
見ないので、**未接続者はレポートに現れない**ためである。

- 出力: 登録者一覧に `first_event` / `last_event` / `ledger_rows` を付し、`events = 0` を **未接続** として
  先頭に出す
- 併せて Cloud Run ログの `not in oauth_identity_map` 拒否を日次で拾い、**拒否された sub があれば
  未登録候補として表示**する(B の検知)
- 受け入れ: 拒否ログに残っている未登録の sub が、レポート初回実行で必ず現れること

> 実装上の注意: 拒否ログにはメールアドレス(生PII)が出る。レポートは既定でマスクし、
> 生値は Cloud Run ログを直接見る運用にする(FLOOR-01)。

### C2(A 対応)— 登録と接続案内を1つの手順にする

identity_map への登録だけ済ませ、接続案内が追随しないと A が起きる。`docs/CONNECT.md` /
`docs/MANUAL_users.md` を**登録直後に本人へ渡す1通**にまとめ、登録スクリプト側から「未案内リスト」を出す。
`oauth_identity_map.claimed_at` があるので、**claimed_at IS NULL = 案内済みだが未接続** として運用指標にできる。

### C3(C 対応)— Stop フックによる督促は設けない

「log_usage 未実行を Stop フックで warn する」案は採らず、C4 に一本化する。理由は2つ:

1. **Stop フックの stdout はモデルに届かない**(`docs/HOOKS_SPEC.md`「warn の届け方」)。届かない以上、
   中身をいくら正しくしても効かない。
2. **C4 が正しく持っている判断を、より悪いデータソースで再導出することになる**。C4 はサーバー側で actor の
   真の scope と未記録状況を知っている。フックはそれをトランスクリプトから推測するので、機械が挿入した
   ターンを人間のプロンプトと数えるなどの偽陽性が出る。しかも R1 の宣言は actor に紐づいてセッションを
   またぐのに、フックは自分のトランスクリプト内の宣言しか見えない。**誤督促は「督促を止める一番安い手＝
   私事を台帳に書く」を作る**ので、外し方の向きが最悪である。

C4 はクライアント非依存で、フックの無い経路(ブラウザ版など)にも同じように効く。

### C4(C 対応)— サーバー側 nudge 【実装済み】

`get_applicable_policy` の応答に、その actor の**直近の未記録状況**を1行添える
(例: `"coverage_hint": "直近5回のポリシー確認のうち2回、記録が残っていません"`)。
tool_events だけで計算でき、内容を一切持たない。

- 助言であって**ブロックではない**(§9.4 と同じ流儀)
- 他人の記録状況は絶対に出さない(自分の actor_id 分のみ)

| | |
|---|---|
| 純ロジック | `ledger/tool_events.py: coverage_hint()` — 行の並びだけを見る。誰の行かは知らない |
| 取得 | 両ストアの `recent_by_actor()`。**actor 述語が ACL** で、SQL 側も1 actor に固定(§3.3 と同じ「見えない行はBQから出さない」形) |
| 組み立て | `ServerContext._coverage_hint()` — actor は `ledger_actor(self.viewer)` 由来のみ。クライアント引数は一切届かない |
| 出方 | 未記録が0なら**黙る**。完了した確認が2回未満でも黙る(常時出る助言は読まれなくなるため) |
| 進行中のターン | 直前の `policy_check` は**数えない**。`get_applicable_policy` は `log_usage` より先に呼ぶ規約(運用ルール1)なので、数えると毎セッションの初回で必ず鳴る |
| 対象外セッション | `external`/`private` を宣言済み(R1 で書き込みが拒否される)なら**出さない**。R1 が `usage_recorded` を止める一方 `policy_check` は出続けるので、放置すると正しく宣言した人ほど督促され、それを止める一番安い手が「他組織・私事を組織の台帳に書く」になる |
| 届け方 | `SYSTEM_PROMPT_RULES` とツール説明の両方に「返ったら1行で伝える」を入れてある。応答に載せるだけではフック無し経路で誰の目にも触れない |

**既知の限界**: 1ターンで `get_applicable_policy` を2回呼ぶと、1回の未記録として数える。連続する確認を
まとめる直し方は、未記録が続く人の N ターンも1つにまとめてしまい C4 が届けたい相手を黙らせるので採らない。
ターン境界はサーバーから観測できない — それが C5 の仕事である。

`window` は5(`COVERAGE_HINT_WINDOW`)。古い未記録は窓から出ていく — 恒久的な成績表ではなく
「直近の数ターン」への助言である。

### C5(D 対応)— 記録率の正しい分母と R7 ファネル

真の分母＝「AI とやり取りしたターン数」はサーバーから観測できない。取り得る近似は2つ:

1. **クライアント側カウンタ**(未実装): クライアントがターン数だけを `tool_events` に薄い行として送る
   (内容なし・件数のみ、R1 の除外メトリクスと同じ流儀)。→ 記録率 = usage_recorded / ターン数 が
   **サーバー側で直接出せる**。カウンタはモデルに話しかける必要がない(行を1本書くだけ)ので、C3 を
   採らない理由は当てはまらない。ただし運び手(フックから MCP ないし HTTP でサーバーを叩く経路と、その認証)
   の設計が要る。
2. **アンケート突合**(SPEC_ops R3c、未実装): 主観の推定値。1 が入るまでの暫定

R7(記録率ダッシュボード)は、**登録者数 → 接続者数 → 記録者数 → 記録率** のファネルとして作る
【R7 ファネルは実装済み】。記録率より手前で落ちることが多いので、記録率単体ではなくファネルであるべきである。

## 4. 実施順序

| 順 | 項目 | 依存 | 状態 |
|---|---|---|---|
| 1 | C1 未接続者・拒否ログの可視化 | なし | 実装済み |
| 2 | C2 登録と案内の一本化 | C1 | 運用＋docs |
| 3 | C4 サーバー側 nudge | なし | 実装済み |
| 4 | R7 ファネル | なし | 実装済み |
| 5 | C5 ターンカウンタ | 運び手の設計 | 未実装 |

C1 と C4 は互いに独立である。C1 が無いと、他の施策の効果を測れない
(使っている人が少数のままでは、記録率を上げても全体は動かない)。

## 5. 受け入れ基準

- **AC-1**: レポートに未接続者と拒否された未登録者が列挙される(C1)
- **AC-2**: 登録から7日以内に接続していない人が0になる運用が回る(C2)
- **AC-3**: `get_applicable_policy` の応答に自分の未記録ヒントが出る。他人の情報は出ない(C4)
  → `tests/test_ops.py`(自分の分が出る/同僚の連続未記録が自分のヒントを1ターンも動かさない/
  未解決 viewer 同士が混ざらない/ヒント計算が落ちても本体は返る)と `tests/test_w2_row_parity.py`
  (双子が行単位で一致し、BQ 側も他 actor の行を返さない)。
- **AC-4**: C5 のターンカウンタが入ったら、記録率が usage_recorded / ターン数 としてサーバー側で出る(未実装)
- **AC-5**: 記録率が「登録→接続→記録」のファネルとして1画面で見える(R7/C5)
  → R7 側は `ledger/tool_events.py: funnel_summary()` ＋ `scripts/coverage_report.py` の冒頭に段の集計を
  出す(個票より前)。段ごとの通過率・未接続・「接続したが1行も書いていない人」を出す。
  `tests/test_coverage_funnel.py`(段の並び/人ベースの率を per-turn と名乗らないこと/分母ゼロで率を
  捏造しないこと/取り下げた人が記録の段から外れること)。C5 のターンカウンタ側は未実装。
- **AC-6**: 上記いずれも**記録をブロックしない**(助言のみ — §9.4 / R8 の流儀)

## 6. 未解決の論点・運用上の注意

- **ターンカウンタ(C5-1)のプライバシー**: 「内容なし・件数のみ」でも、新たに個人の行動を測る器を
  持つことになる。導入する組織が判断する。R7 の `connected_but_silent` はこれに当たらない — この数字を
  見るのは同じレポートで `person_id` つきの個票を既に見ている管理者であり、集計を足しても新しく見える
  ものは無い(既にある器の畳み直しにすぎない)。この整理が効くのは**このレポートの中だけ**である。
- **個人別表示は「二値と欠落」だけにする**: 接続済み/未接続、直近N日に記録あり/なし の別と、欠落者の
  列挙まで。件数・分布・ランキングを個人に紐づけて出さない。数字が見えていれば書き出して並べられるので、
  **数字を出さないことでしか防げない**。`scripts/coverage_report.py` の実装(人数下限のしきい値つき)は
  これに従う。
- **用途の限定**: `connected_but_silent` は名前の並ぶ個票の2行上に出る見出しなので、そのままでは
  勤務評価の材料に読める。レポートに「施策の効果測定であり個人の勤務評価には用いない」を印字している。
  **印字は運用の歯止めであって技術的なゲートではない**。台帳と記録率を懲戒・人事評価の減点に使わないこと。
- **小さい母数**: 登録5名未満のとき「切り出して共有しないこと」を併記する。抑止はしていない(管理者向けの
  資格つきスクリプトなので真の値は見えてよい)。**この見出しをダッシュボード・定期メール・MCP ツールなど
  他の面に出すなら、そちらでは最小セル抑止が要る。率も 4桁に丸めているので分母が割れる — 伏せるなら
  率も伏せること。**
- **フックも MCP も無い経路**(MCP 非対応のチャットなど)の扱い
- 拒否ログの保持期間(Cloud Run 既定)を超えた分の検知漏れ → ログシンクの要否
