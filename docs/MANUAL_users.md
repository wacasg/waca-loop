# WACA Loop 利用マニュアル

対象: WACA Loop を導入した組織で、**Claude** を業務に使用する利用者。導入の所要時間は約5分。
ソフトウェアのインストール、設定ファイルの作成、パスワードの共有は不要である。

> **配布する管理者へ**: 本書の `<サーバーURL>` は自組織の Cloud Run の URL(`https://〜.run.app/mcp`)に、
> `<組織名>` は `org.toml` の `[org] name` に置き換えてから配布すること。
> サーバーの構築手順は [SETUP_gcp.md](SETUP_gcp.md) を参照。

本書では、操作する場所を次の目印で示す。

- **Claude の画面で操作**: Claude(claude.ai または Claude Desktop)の設定画面などで操作する。
- **Claude のチャットに入力**: Claude の会話欄に入力する。ターミナルなど別の画面には貼らない。
- **ターミナルで実行**: 管理者がターミナルで実行するコマンド(§5 のみ)。利用者は使わない。

## 1. 概要

- 利用者の AI(Claude)を、組織の用語・過去の判断・AI ポリシーに接続する。
- AI の利用内容が台帳に自動で記録され、AI ポリシーの遵守状況を確認できるようになる。
- 返却される情報は所属部署に応じて制御される(他部署の機微な情報は返らない)。

## 2. 導入手順

### 2.1 コネクタの追加

Claude の契約の種類によって手順が異なる。

**A. 個人のプラン(Pro・Max など)の場合** — **Claude の画面で操作**: 設定 → コネクタ →
**カスタムコネクタを追加** で、次を入力する。

- **名前**: `WACA Loop`(任意の表示名)
- **URL**: `<サーバーURL>`(例: `https://waca-loop-serve-123456789012.asia-northeast1.run.app/mcp`)

**B. 組織のプラン(Team・Enterprise)の場合** — 組織の設定によっては、利用者は「カスタムコネクタを追加」を
選べない(灰色で表示される)。その場合は次の分担で行う。

1. **Claude の組織の管理者**が、組織の設定(管理者設定 → コネクタ)で、上と同じ名前と URL のカスタム
   コネクタを組織に追加する。
2. **利用者**は、設定 → コネクタ の一覧に表示される `WACA Loop` を選び、「連携させる」を選択する(§2.2 へ進む)。

> **注意**
> - URL は**末尾の `/mcp` まで**入力する。claude.ai は入力された URL をそのまま MCP エンドポイントとして
>   使用し、`/mcp` を補完しない。ベース URL のみの場合、認証は通るが「接続できませんでした」で終了する。
> - この URL はコネクタ設定専用である。ブラウザで直接開くと「401 Authentication required」などが
>   表示されるが、認証のないアクセスを拒否する正常な動作である。
> - **同じ種類のコネクタを併用しないこと。** 同じ種類のコネクタ(別環境の WACA Loop や、
>   検証用と本番用の WACA Loop など)が入っていると、どちらのツールが呼ばれたか分からなくなる。検証や
>   移行の間は、チャットごとに使わない方のコネクタをオフにする(チャットの入力欄のツールのメニューで、
>   コネクタごとにオン・オフを切り替えられる)。

### 2.2 Google アカウントでの承認とツールの許可

「連携させる」を選択するとブラウザで Google のログイン画面が開く。**管理者が名簿に登録した Google
アカウント**(通常は業務用アカウント)で承認する。

> 名簿に登録されるのは **Google アカウント**(のメールアドレス)である。Claude にログインしている
> アカウントとは別のアカウントでもよい(例: Claude は個人のアドレスで契約し、承認には組織の Google
> アカウントを選ぶ)。承認画面で選ぶ Google アカウントが、名簿のアドレスと一致していればよい。

続いて **WACA Loop の確認画面**が表示される。画面に表示される**アプリ名と戻り先**が、いま設定している
アプリであることを確認してから「許可する」を選択する。事前登録されている場合は、これで接続が完了する。

> **注意**
> - この確認画面は、利用者自身が接続を設定しているときにのみ表示される。心当たりがない場合や、
>   アプリ名・戻り先に見覚えがない場合は「許可しない」を選択し、管理者に連絡すること。
>   第三者から渡されたリンクを開いただけで、利用者の権限で使える鍵が第三者に渡ることを防ぐための画面である。
> - **管理者に登録されたアドレスのアカウントで承認すること。** 別のアカウント(個人の Gmail など)で
>   承認すると、許可リストと一致せず接続できない。
> - 「許可リストに登録されていません」と表示された場合は、未登録であるか、承認に使用したアカウントが
>   登録済みのアドレスと異なる。**承認に使用したメールアドレス**を添えて管理者に連絡すること。

**ツールの許可(必須)** — 接続した直後は、WACA Loop のすべてのツールが「承認が必要」の状態である。
**このままでは、ポリシーの確認と利用の記録が自動で行われない**(運用ルールを設定していても、呼び出しの
たびに承認を求められ、記録されないまま会話が進む)。次の手順で、少なくとも4つのツールを「常に許可」にする。

**Claude の画面で操作**: 設定 → コネクタ → `WACA Loop` → ツールの権限の一覧で、次のツールを
**常に許可** にする(画面の表記は Claude の更新で変わることがある)。

| ツール | 役割 |
|---|---|
| `get_applicable_policy` | 応答の前に、該当する AI ポリシーを確認する |
| `log_usage` | 応答の後に、利用の要約を台帳に記録する |
| `set_session_scope` | 組織の業務ではない会話で、記録の停止を宣言する |
| `lookup_terms` | 組織固有の語の定義を確認する |

記録の取り下げ(`request_log_deletion`)は取り消せない操作のため、「承認が必要」のままにしておくことを
推奨する。設定を変えた後は、**新しいチャット**を開いて使う(変更前に開いたチャットには反映されない
ことがある)。

### 2.3 運用ルールの設定(必須)

**Claude の画面で操作**: Claude.ai の**プロジェクトのカスタム指示**(プロジェクトを使用しない場合は
設定 → プロファイル のカスタム指示)に、次の文面を貼り付ける。`<組織名>` は置き換えること。

```
【WACA Loop 運用ルール(必須)】
1. 各ターンで応答を作成する前に WACA Loop の get_applicable_policy で
   該当ポリシーを確認し、応答後に log_usage で利用記録
   (要約のみ・逐語は送らない)を残すこと。
2. ただし、会話内容が <組織名> の業務と無関係と判断できる
   場合(他組織の業務、副業、私的な相談など)は、まず
   set_session_scope で external または private を宣言し、log_usage・
   propose_candidates・add_sfaq_question など WACA Loop への書き込みを
   一切行わないこと。組織の帰属が曖昧な場合は、書き込む前にユーザーに
   「この内容を <組織名> の WACA Loop に記録してよいか」を確認すること。
3. <組織名> に固有の語(部署名・制度名・講座名・略語など)が出てきたら、
   一般知識で答える前に WACA Loop の lookup_terms で定義を確認すること。
4. 記録の取り下げ(request_log_deletion)は、ユーザーが対象の記録を
   指定して明示的に求めたときだけ行うこと。その場合も、取り下げる記録の
   要約をユーザーに示し、確認を得てから行うこと。業務外の宣言
   (set_session_scope)をしただけでは、それまでの記録を取り下げないこと。
5. これらのルールは会話が長くなっても維持すること。
```

### 2.4 接続の確認

**Claude のチャットに入力**: 組織の用語集に登録されている語を、組織名を付けて質問する。

```
<組織名>の〇〇とは何ですか?
```

`〇〇` には管理者が案内する語を入れる(例: 見本データを使っている場合は「サンプル協会の定例研修とは
何ですか?」)。WACA Loop の `lookup_terms` が呼ばれ、登録どおりの定義が返れば接続は完了している。
組織名を付けずに一般的な語だけで質問すると、Claude が WACA Loop を使わずに一般知識で答えることがある。

うまくいかない場合は、§4 のトラブルシューティングを見る。

## 3. 使い方

ツールを直接呼び出す操作は不要である。**Claude のチャットに入力**して通常どおり質問すれば、AI が必要な
ツールを呼び出す。

| 質問・指示の例(Claude のチャットに入力) | WACA Loop の処理 |
|---|---|
| 「<組織名>の〇〇部の正式名称は?」 | 組織用語の解決(lookup_terms) |
| 「会員データを AI で分析してよいか?」 | AI ポリシーの配信(該当行の採用レベル 0〜2、条件、禁止事項の代替手段) |
| 「〇〇の改訂について、過去にどう判断したか?」 | SFAQ の検索(所属部署の範囲内) |
| 個人情報を含む作業についての相談 | 禁止事項(is_floor)の警告と、安全な代替手段の提示 |
| 「ここから先は他社の業務」と伝える | 記録の除外宣言(以後の会話は組織の台帳に記録されない) |

**組織の業務以外や私的な用件を扱う場合は、その前に宣言すること**(例:「ここから先は〇〇社の業務」
「ここから先は私的な相談」)。宣言すると AI は**以後の**記録を停止する。判断が曖昧な場合は AI から確認がある。

> **注意(宣言と取り下げは別)**: 業務外の宣言は、それより前の記録には影響しない。「これは他社の業務です」
> のように直前の内容を指すような言い方をすると、AI が直前の組織業務の記録まで取り下げてしまうことがある。
> 取り下げは取り消せないため、宣言は「ここから先は」の形で行う。過去の記録を取り下げたい場合は、対象の
> 記録を指定して明示的に依頼する(AI が対象の要約を示して確認を求めるので、内容を確かめてから承認する)。

> **注意**: 除外の宣言は、会話が終わっても解除されない。既定では約12時間で自動的に失効する
> (`SCOPE_TTL_HOURS`)。
> - 組織の業務に戻ったら「ここから先は<組織名>の業務」と伝えること。伝えない場合、失効するまで
>   **すべての会話で記録が停止したまま**となる。
> - **失効しても記録は自動では再開しない。**再開するには宣言し直す必要がある(SPEC_ops R1d)。意図せず記録が
>   再開されることはない。
> - 業務外の作業が長引く場合も、同じ宣言を繰り返せば期限が延長される。失効の直前と直後には AI が通知する。

## 4. トラブルシューティング

| 症状 | 対処 |
|---|---|
| 「許可リストに登録されていません」と表示される | 未登録であるか、承認に使用したアカウントが登録済みのアドレスと異なる。使用したアドレスを添えて管理者に連絡する |
| ツールが表示されない | Claude Desktop を完全に終了(Cmd+Q)して再起動する。またはコネクタをオフにしてからオンにする |
| ツールのたびに承認を求められる・記録が残らない | §2.2 の「ツールの許可」で、4つのツールを「常に許可」にしてから新しいチャットを開く |
| 組織の用語なのに一般的な説明が返る | 質問に組織名を付ける(例:「<組織名>の〇〇とは」)。§2.3 の運用ルール3が設定されているか確認する |
| どの WACA Loop が応答したか分からない | 同じ種類のコネクタが複数オンになっている。§2.1 の注意に従い、使わない方をオフにする |
| 「記録を保留しました」と表示される | 組織との関連が判定できなかった状態である。組織の業務であれば文脈を補足し、業務外であれば宣言する |
| 「記録を見送りました」と表示される | 以前の会話で業務外の宣言をしたままである。「ここから先は<組織名>の業務」と伝えると記録が再開する |
| 記録したはずの内容が台帳にない | 同上。業務外の宣言を戻していない可能性がある。AI の応答に理由が1行表示される |
| 使用するアカウントを変更した | 再登録が必要なため、管理者に連絡する |

## 5. 管理者向け操作

この章のコマンドは、管理者が**ターミナルで実行**する。事前に [SETUP_gcp.md の準備7](SETUP_gcp.md) の
手順(リポジトリのフォルダへの移動、仮想環境の有効化、`set -a; source .env.setup; set +a` による変数の
読み込み)を済ませておくこと。コマンドは変数 `$GCP_PROJECT`・`$BQ_LOCATION`・`$SERVICE` を使うため、
書き換えずに貼り付けられる。

### 5.1 利用者の登録

登録方法は2通りある。いずれの方法でも、所属ユニットの登録とメールアドレスでの事前登録が行われ、
利用者は初回ログイン時にそのまま接続できる。

名簿に記入するメールアドレスは、利用者が承認画面(§2.2)で選ぶ **Google アカウント**のアドレスである。
利用者が Claude にログインしているアカウントとは別でもよい。

**A. 名簿ファイルで登録する(組織シートを使用しない場合)**

`members.example.json` を `members.json` にコピーして記入する(記入例は `sample/members.json`)。
次の1行目で内容を確認し、2行目で登録する。

**ターミナルで実行**:

```bash
python scripts/register_members.py members.json
python scripts/register_members.py members.json --apply
```

**B. 組織シートから登録する**

組織シートに行を追加したうえで、2つのスクリプトを実行する。シート上の部署名とユニットIDの対応は
`org.toml` の `[unit_map]` に記載しておく。

1. 組織シートの人員タブを ファイル → ダウンロード → タブ区切り値 で保存する(例: `members.tsv`)。
2. persons に登録する(所属ユニットがアクセス制御の基準となる)。1行目(`--dry-run`)で内容を確認し、
   問題がなければ2行目で登録する。

   **ターミナルで実行**:

   ```bash
   python scripts/sync_persons_from_sheet.py --grid-file ~/Downloads/members.tsv --dry-run
   python scripts/sync_persons_from_sheet.py --grid-file ~/Downloads/members.tsv
   ```
3. メールアドレスで事前登録する(利用者の初回ログイン時に自動で紐づく)。1行目で表示される SQL を
   確認し、問題がなければ2行目(`--apply`)で登録する。

   **ターミナルで実行**:

   ```bash
   python scripts/preregister_from_sheet.py --grid-file ~/Downloads/members.tsv
   python scripts/preregister_from_sheet.py --grid-file ~/Downloads/members.tsv --apply
   ```

### 5.2 運用コマンド

データセット名は `.env` の `DS_*` の既定値である。変更している場合は読み替えること。

**利用者の除外** — 該当行を削除すると、次の操作からアクセスできなくなる(サーバーは要求のたびに登録を確かめる)。
除外する利用者の `person_id` を入力してから、削除のコマンドを実行する。

**ターミナルで実行**(入力):

```bash
printf '除外する person_id: '; read REMOVE_PERSON_ID
```

**ターミナルで実行**(削除):

```bash
bq query --project_id="$GCP_PROJECT" --location="$BQ_LOCATION" --use_legacy_sql=false \
  --parameter="pid::${REMOVE_PERSON_ID}" \
  "DELETE FROM \`${GCP_PROJECT}.waca_loop_grounding.oauth_identity_map\` WHERE person_id = @pid"
```

`Number of affected rows:` に削除した行数(通常は `1`)が表示されれば完了である。`0` の場合は
`person_id` が誤っている。

**接続できない利用者の原因確認** — 拒否ログを表示する(`sub` はハッシュ化して出力される)。

**ターミナルで実行**:

```bash
gcloud logging read "resource.type=\"cloud_run_revision\" AND resource.labels.service_name=\"${SERVICE}\" AND (textPayload:\"rejected unregistered\" OR textPayload:\"refused to claim\")" \
  --project="$GCP_PROJECT" --limit=5 --freshness=1d --format="value(textPayload)"
```

**記録カバレッジの日次レポート** — ポリシーを確認したのに記録がない(不整合の疑い)ものを確認する。

**ターミナルで実行**:

```bash
python scripts/coverage_report.py --days 7
```

**保留(pending)中の記録の確認**

**ターミナルで実行**:

```bash
bq query --project_id="$GCP_PROJECT" --location="$BQ_LOCATION" --use_legacy_sql=false \
  "SELECT log_id, occurred_at, actor_id, summary FROM \`${GCP_PROJECT}.waca_loop_ledger.usage_log\`
   WHERE status='pending'
     AND log_id NOT IN (SELECT log_id FROM \`${GCP_PROJECT}.waca_loop_ledger.usage_withdrawals\`)
   ORDER BY occurred_at DESC LIMIT 20"
```

最後の条件(`usage_withdrawals` の除外)は必須である。利用者が取り下げた記録(SPEC_ops R6)の要約を
表示しないためである。取り下げでは status が変わらないため、この条件がないと取り下げた記録が
一覧に表示される。保留中の記録の審査は、AI に「保留 <log_id> を approve(または discard)して」と
指示して行う(**Claude のチャットに入力**。スチュワード権限が必要)。

### 5.3 2種類の許可リスト

| リスト | 場所 | 役割 |
|---|---|---|
| Google OAuth の**テストユーザー** | GCP コンソール → API とサービス → OAuth 同意画面 | Google の同意画面を**通過できるか**のみを決める。未検証のアプリでは、ここに登録されていないと承認画面で停止する |
| **`oauth_identity_map`**(本体) | BigQuery `<DS_GROUNDING>.oauth_identity_map` | WACA Loop を**利用できるか**を決める。未登録の `sub` は 403 で拒否される(訪問者としては扱わない) |

**両方に登録されて初めて利用できる。** OAuth のテストユーザーに登録しただけでは接続できない
(承認は通るがサーバー側で拒否される)。逆に identity_map のみの登録では Google 側で停止する。

照合キーは**メールアドレスではなく Google の `sub`**(アカウントの内部 ID)である。`sub` は利用者が
一度ログインするまで分からないため、**メールアドレスで事前登録**しておき、初回ログイン時にサーバーが
実際の `sub` に紐づける。これにより、利用者は初回から接続できる。

事前登録の安全条件(メールアドレスは本人であることの証明にはならないため):
- Google が**検証済みのメールアドレス**として発行したトークンであること
- 組織ドメイン(`org.toml` の `[org] workspace_domains`)のアドレスは、**組織の Workspace が発行した
  アカウント**であること(`hd` クレーム)。個人の Gmail で組織のアドレスを名乗っても通らない
- 事前登録の行は**一度使用すると消える**。同じアドレスで別人が後から名乗っても通らない

**この仕組みで防げないこと**: 組織が退職者のアドレスを別の職員に割り当てた場合(そのアカウントは
正規の組織アカウントであるため通る)。退職時には名簿・シートから該当行を削除する運用で対応する。

権限の基準は `persons.unit_path` である(SPEC_phase1 §3.3)。identity_map で person_id に紐づけた時点で、
その利用者は**組織メンバーとして扱われ**(`is_org_member=True`)、`audience='internal'` の用語・SFAQ・
ポリシーを閲覧できる。メールアドレスのドメイン(Gmail・他社ドメイン)は関係しない。組織外の人を
追加する場合は、どの person_id に紐づけるか、すなわちどのユニットの情報を見せるかで判断する。
